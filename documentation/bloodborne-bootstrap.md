# Bloodborne CUSA03173 1.09 HTTP bootstrap

This server-side bootstrap is intentionally limited to the network contracts demonstrated from
the CUSA03173 1.09 executable. It does not patch Bloodborne, replace `ResKind`, or alter the
existing summon broker.

## Configuration

The feature is disabled by default. Set both values in the `shadnet.cfg` beside `shadnet.exe`:

```ini
BloodborneBootstrapEnabled=true
BloodbornePublicBaseUrl=http://100.101.102.103:31315
```

`BloodbornePublicBaseUrl` must be the address the players can actually reach. Do not use
`0.0.0.0`, and do not include a path, query string, or fragment. Startup fails with a clear error
if the bootstrap is enabled without a valid HTTP(S) URL.

Optional request/response logging is enabled with:

```text
SHADNET_BLOODBORNE_BOOTSTRAP_TRACE=1
```

The local trace prints only API, user, method, path, status, and `ResKind`. It never prints
`AuthorizationCode` or complete game data. Recognized blob fields are represented only by byte
count and SHA-256. The existing summon trace and seamless co-op settings are unchanged.

## Temporary reference proxy

The development-only reference proxy is disabled by default. It must never be enabled on the
final independent server. To capture one reference session, add:

```ini
BloodborneBootstrapEnabled=true
BloodborneReferenceProxyEnabled=true
BloodborneReferenceProxyUrl=http://thehuntersdream.com:18671
```

`BloodborneReferenceProxyEnabled=true` is rejected unless the bootstrap is also enabled. The
upstream URL must be an HTTP(S) base URL without a path, query, or fragment. In this mode shadNet
continues to serve its embedded golden Base64 `/bb-eu/ss.info`, and the four
`/summon_messenger/*` routes always remain on the local `Bloodborne::SummonBroker`. All other
known Bloodborne backend prefixes are forwarded without changing their method, path, query, body,
Content-Type, User-Agent, status, or response body. Login is deliberately forwarded only in this
temporary mode so the upstream creates its own `UserId` and `SessionId`.

Enable sanitized console tracing before starting shadNet:

```powershell
$env:SHADNET_BLOODBORNE_REFERENCE_TRACE="1"
.\shadnet.exe
```

Every proxied operation is also written beneath:

```text
captures/bloodborne-reference/<UTC timestamp>/
```

The directory contains `manifest.jsonl`, numbered request/response bodies, `summary.json`, and
`summary.txt`. JSON authentication values such as `AuthorizationCode`, passwords, tokens, and
bearer values are replaced with `<redacted>` in both console and disk captures. The original body
is still forwarded byte-for-byte to the configured upstream. Disable the mode after the capture:

```ini
BloodborneReferenceProxyEnabled=false
```

## Client host override

Only the Sony server-status host needs redirecting. Replace the example IP with the shadNet
server address:

```json
{
  "https://ss4.scej-network.jp:20443": "http://100.101.102.103:31315"
}
```

No `thehuntersdream.com` rule is required. The `ss.info` generated by shadNet publishes the same
private base URL in all 37 `api_*` values. Bloodborne appends each endpoint path later.

## Demonstrated `ss.info` contract

The parser formats the internal game URL index directly as `<gameurl%u>`. For this executable the
value is `2`, so the required container is `gameurl2`; there is no `+1` conversion. The parser
locates both container boundaries and checks every API opening and closing tag inside that range.
Any missing API tag makes the complete parse fail.

The HTTP response body is Base64. Bloodborne decodes it before parsing; the decoded XML starts
with:

```xml
<ss>0</ss>
<gameurl2>
```

It then emits exactly these 37 mappings, where every value is the same
`BloodbornePublicBaseUrl` without a trailing slash:

```text
api_Login                              BASE
api_ServerTimeGet                      BASE
api_SyncCharaId                        BASE
api_NoticeNormalGet                    BASE

api_UserAgreementGet                   BASE
```

The functional reference demonstrates that Bloodborne appends the endpoint path after parsing the
base. For example, `api_Login=BASE` becomes `BASE/basic_utils/login`, and
`api_SummonDataCreate=BASE` becomes `BASE/summon_messenger/create`. The latter remains the existing
Wozzardman route and shared `Bloodborne::SummonBroker`; no second broker is created.

After `gameurl2`, shadNet emits the matching intervals, level ranges, guard timers, and PlayLog
flags captured from the functional response. `msg2` is retained with the demonstrated empty
language entries. `BetaTestWebUrl2` is retained but its language values are empty, avoiding any
Sony URL dependency.

## Demonstrated bootstrap contracts

All demonstrated game API requests use HTTP `POST`. The request builder selects method enum `1`,
which is passed to `sceHttpCreateRequestWithURL`, and sends the serialized JSON as the request
body. This path does not call `sceHttpAddRequestHeader`, so CUSA03173 does not explicitly add a
Content-Type header. shadNet parses the body as JSON without requiring that header.

Every request includes `MessageId`. Except for Login and UserAgreement, the common serializer also
adds numeric `UserId`, string `SessionId`, and the URL query `?user_id=<UserId>`.

### Login

Path: `POST /basic_utils/login`

Request fields and types:

```json
{
  "MessageId": "LoginRequest",
  "PlatformAccountId": "string",
  "AuthorizationCode": "string",
  "NatType": 0,
  "RegionId": 0,
  "LanguageId": 0,
  "IssuerId": 0,
  "ApplicationVersion": 6
}
```

The strings may be empty in an emulated NP environment; shadNet does not use them as credentials.
When `PlatformAccountId` names a currently authenticated TCP shadNet client, that exact NPID is
used. If an NP stub leaves the field empty, the HTTP connection is correlated with the unique
already-authenticated TCP client from the same peer address. An absent or ambiguous TCP identity
is rejected rather than assigning a shared fallback account.

The response parser reads exactly `ResKind`, `UserId`, `UserStatus`, `LanguageId`, `SessionId`, and
`ServerVersion`. The observed continuation gate requires `ResKind == 0`, a non-sentinel `UserId`,
and a non-empty `SessionId`. `UserStatus` and `ServerVersion` are stored but are not compared on
this continuation path. shadNet returns the real account ID, echoes the requested language, creates
a unique session UUID, and reports application/server version `6`:

```json
{
  "MessageId": "LoginResponse",
  "ResKind": 0,
  "UserId": 1,
  "UserStatus": 0,
  "LanguageId": 4,
  "SessionId": "per-login UUID",
  "ServerVersion": 6
}
```

The local response also includes the demonstrated `"MessageId":"LoginResponse"`.

### ServerTimeGet

Path: `POST /basic_utils/get_datetime`

The API URL and request ID `ServerTimeGetRequest` exist, but this executable has no direct call site
that submits API index `1`, and its response switch has no API-specific parser for index `1`.
Only the common `ResKind` parser applies. The implemented minimal response is therefore:

```json
{"ResKind":0}
```

No time field is invented. `CheckTime` is demonstrated elsewhere as part of the emergency-notice
contract, not as an API-index-1 response field.

### NoticeNormalGet

The real post-Login continuation first submits API index `3`, not ServerTimeGet or SyncCharaId. Its
request contains `Language`, `Region`, and the common session fields. The response parser requires
`NoticeList` to be an array; an empty array follows its valid zero-item path:

```json
{"MessageId":"NoticeNormalGetResponse","NoticeList":[],"ResKind":0}
```

### NoticeEmergencyGet

The next demonstrated request uses API index `4` and sends `Language`, `Region`, and `CheckTime`.
The response parser reads `CheckTime` using the demonstrated `yyyy-MM-ddTHH:mm:ss` format and a
`NoticeList` array. shadNet copies `CheckTime` from the request and returns an empty list.

```json
{"CheckTime":"request value","MessageId":"NoticeEmergencyGetResponse","NoticeList":[],"ResKind":0}
```

## Local minimum Online endpoints

With `BloodborneReferenceProxyEnabled=false`, shadNet serves the accepted local Login and these
captured bootstrap/keepalive contracts:

- `POST /basic_utils/get_normal_notice`
- `POST /basic_utils/get_emergency_notice`
- `POST /penalty/check_user_priority_move_count`
- `POST /blood_messenger/exist_messages`
- `POST /messenger_shell/upload`
- `POST /wandering_ghost/get`
- `POST /chair_messenger/get`
- `POST /channel/get_info`
- `POST /blood_messenger/evaluation`
- `POST /blood_messenger/message_area`
- `POST /tomb_messenger/message_area`

The message/ghost/chair/channel/tomb list routes deliberately return demonstrated empty-list
success responses; persistence is not implemented. Every endpoint validates the `UserId` and
`SessionId` created by local Login. The four `/summon_messenger/*` endpoints are not part of this
bootstrap handler and remain owned by the existing `Bloodborne::SummonBroker`.

Unknown Bloodborne backend paths return HTTP 404 and emit `[BLOODBORNE LOCAL UNIMPLEMENTED]`;
they are never treated as success automatically.

### SyncCharaId

Path: `POST /basic_utils/sync_chara_id?user_id=<UserId>`

The API-specific request field is numeric `CharaIdNum`; this build sends `1`. The response parser
requires an array of objects:

```json
{
  "ResKind": 0,
  "PublishCharacterIdList": [
    {"PublishCharaId": 1}
  ]
}
```

The request contains no save fingerprint or client character identifier. Consequently, shadNet
assigns persistent IDs by `(shadNet account, requested slot)` in the `bloodborne_character` SQLite
table. Two accounts cannot receive the same ID, and repeated Sync requests for the same account and
slot return the same ID. That ID is then used by the existing summon request bodies as `CharaId` or
`TargetCharaId`.

## API scope classification

This is a goal-oriented classification based on the captured successful Online session:

- A — bootstrap/Online: Login, NoticeNormalGet, NoticeEmergencyGet, SyncCharaId, and
  UserPropertiesMoveCountCheck.
- B — captured keepalive/optional calls with demonstrated minimal responses: BloodMessSearchAdd,
  MessengerShellUpload, WanderingGhostGet, ChairMessGetList, ChannelGetInfo,
  BloodMessGetEvaluate, BloodMessGetList, and TombMessGetList.
- C — optional feature services not implemented in this phase: create/evaluate/remove messages,
  DeathVision, persistent ghosts/chairs, full channels/chalices, and UserAgreement.
- D — co-op: SummonDataCreate, SummonDataGetList, SummonDataRemove, SummonDataSummon. These already
  use the existing summon broker.
- E — not required by the demonstrated CUSA03173 startup path: ServerTimeGet,
  MultiPlayNetError, and UserPropertiesMoveCount.

Only the captured A/B contracts and D are implemented for this phase. Category C endpoints remain
published in `ss.info` because the parser requires all tags, but unknown calls return HTTP 404 and
the explicit local-unimplemented diagnostic.

## Expected incremental test

With tracing enabled, the first bootstrap line is the `ss.info` GET. If its parser succeeds, the
next important line must be:

```text
[BLOODBORNE LOCAL REQUEST] api=Login user_id=0 method=POST path=/basic_utils/login
```

After a valid Login response, the next demonstrated endpoint is
`/basic_utils/get_normal_notice`. If execution instead reaches an unimplemented path, the ordinary
WebAPI missing-handler log identifies that exact next API without fabricating a response.
