# Bloodborne CUSA03173 1.09 HTTP bootstrap

This server-side bootstrap is intentionally limited to the network contracts demonstrated from
the CUSA03173 1.09 executable. It does not patch Bloodborne, replace `ResKind`, or alter the
existing summon broker.

## Configuration

The feature is disabled by default. Set both values in the `shadnet.cfg` beside `shadnet.exe`:

```ini
BloodborneBootstrapEnabled=true
BloodbornePublicBaseUrl=http://100.101.102.103:31315
```

`BloodbornePublicBaseUrl` must be the address the players can actually reach. Do not use
`0.0.0.0`, and do not include a path, query string, or fragment. Startup fails with a clear error
if the bootstrap is enabled without a valid HTTP(S) URL.

Optional request/response logging is enabled with:

```text
SHADNET_BLOODBORNE_BOOTSTRAP_TRACE=1
```

`AuthorizationCode`, passwords, tokens, and secrets are redacted. The existing summon trace and
seamless co-op settings are unchanged.

## Client host override

Only the Sony server-status host needs redirecting. Replace the example IP with the shadNet
server address:

```json
{
  "https://ss4.scej-network.jp:20443": "http://100.101.102.103:31315"
}
```

No `thehuntersdream.com` rule is required. The `ss.info` generated by shadNet publishes all
Bloodborne API URLs, including the four summon URLs, directly on the configured private server.

## Demonstrated `ss.info` contract

The parser formats the internal game URL index directly as `<gameurl%u>`. For this executable the
value is `2`, so the required container is `gameurl2`; there is no `+1` conversion. The parser
locates both container boundaries and checks every API opening and closing tag inside that range.
Any missing API tag makes the complete parse fail.

The response starts with:

```xml
<ss>0</ss>
<gameurl2>
```

## Demonstrated bootstrap contracts

All demonstrated game API requests use HTTP `POST`. The request builder selects method enum `1`,
which is passed to `sceHttpCreateRequestWithURL`, and sends the serialized JSON as the request
body. This path does not call `sceHttpAddRequestHeader`, so CUSA03173 does not explicitly add a
Content-Type header. shadNet parses the body as JSON without requiring that header.

Every request includes `MessageId`. Except for Login and UserAgreement, the common serializer also
adds numeric `UserId`, string `SessionId`, and the URL query `?user_id=<UserId>`.

### Login

Path: `POST /basic_utils/login`

Request fields and types:

```json
{
  "MessageId": "LoginRequest",
  "PlatformAccountId": "string",
  "AuthorizationCode": "string",
  "NatType": 0,
  "RegionId": 0,
  "LanguageId": 0,
  "IssuerId": 0,
  "ApplicationVersion": 6
}
```

The strings may be empty in an emulated NP environment; shadNet does not use them as credentials.
When `PlatformAccountId` names a currently authenticated TCP shadNet client, that exact NPID is
used. If an NP stub leaves the field empty, the HTTP connection is correlated with the unique
already-authenticated TCP client from the same peer address. An absent or ambiguous TCP identity
is rejected rather than assigning a shared fallback account.

The response parser reads exactly `ResKind`, `UserId`, `UserStatus`, `LanguageId`, `SessionId`, and
`ServerVersion`. The observed continuation gate requires `ResKind == 0`, a non-sentinel `UserId`,
and a non-empty `SessionId`. `UserStatus` and `ServerVersion` are stored but are not compared on
this continuation path. shadNet returns the real account ID, echoes the requested language, creates
a unique session UUID, and reports application/server version `6`:

```json
{
  "ResKind": 0,
  "UserId": 1,
  "UserStatus": 0,
  "LanguageId": 4,
  "SessionId": "per-login UUID",
  "ServerVersion": 6
}
```

No response `MessageId` is emitted: this executable never looks up `MessageId` while parsing a
response.

### ServerTimeGet

Path: `POST /basic_utils/get_datetime`

The API URL and request ID `ServerTimeGetRequest` exist, but this executable has no direct call site
that submits API index `1`, and its response switch has no API-specific parser for index `1`.
Only the common `ResKind` parser applies. The implemented minimal response is therefore:

```json
{"ResKind":0}
```

No time field is invented. `CheckTime` is demonstrated elsewhere as part of the emergency-notice
contract, not as an API-index-1 response field.

### NoticeNormalGet

The real post-Login continuation first submits API index `3`, not ServerTimeGet or SyncCharaId. Its
request contains `Language`, `Region`, and the common session fields. The response parser requires
`NoticeList` to be an array; an empty array follows its valid zero-item path:

```json
{"ResKind":0,"NoticeList":[]}
```

### NoticeEmergencyGet

The next demonstrated request uses API index `4` and sends `Language`, `Region`, and `CheckTime`.
The response parser reads `CheckTime` using the demonstrated `yyyy-MM-ddTHH:mm:ss` format and a
`NoticeList` array. shadNet returns current UTC server time and an empty list.

### SyncCharaId

Path: `POST /basic_utils/sync_chara_id?user_id=<UserId>`

The API-specific request field is numeric `CharaIdNum`; this build sends `1`. The response parser
requires an array of objects:

```json
{
  "ResKind": 0,
  "PublishCharacterIdList": [
    {"PublishCharaId": 1}
  ]
}
```

The request contains no save fingerprint or client character identifier. Consequently, shadNet
assigns persistent IDs by `(shadNet account, requested slot)` in the `bloodborne_character` SQLite
table. Two accounts cannot receive the same ID, and repeated Sync requests for the same account and
slot return the same ID. That ID is then used by the existing summon request bodies as `CharaId` or
`TargetCharaId`.

## API scope classification

This is a static, goal-oriented classification, not a claim that every optional feature has been
dynamically exercised:

- A — bootstrap/Online: Login, NoticeNormalGet, NoticeEmergencyGet, SyncCharaId.
- B — safe minimal empty response: NoticeNormalGet and NoticeEmergencyGet, already included in A.
- C — optional feature services: all BloodMess, Channel, MessengerShell, ChairMess, TombMess,
  DeathVision, and WanderingGhost APIs.
- D — co-op: SummonDataCreate, SummonDataGetList, SummonDataRemove, SummonDataSummon. These already
  use the existing summon broker.
- E — not required by the demonstrated CUSA03173 startup path: ServerTimeGet, UserAgreementGet,
  MultiPlayNetError, UserPropertiesMoveCount, and UserPropertiesMoveCountCheck.

Only A and D are in scope for reaching Online and ringing bells. Category C endpoints remain
published in `ss.info` because the parser requires all tags, but shadNet does not pretend to
implement their protocols.

## Expected incremental test

With tracing enabled, the first bootstrap line is the `ss.info` GET. If its parser succeeds, the
next important line must be:

```text
[BLOODBORNE BOOTSTRAP REQUEST] api=Login method=POST path=/basic_utils/login
```

After a valid Login response, the next demonstrated endpoint is
`/basic_utils/get_normal_notice`. If execution instead reaches an unimplemented path, the ordinary
WebAPI missing-handler log identifies that exact next API without fabricating a response.
